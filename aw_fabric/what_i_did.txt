--Ingestion aka Bronze Layer--
things are overwriting
Made 2 Lakehouses and 1 Warehouse
Ran SQl Query inside warehouse to make 'dbo.ETL_Log' (its a error diary for the Gold load suggested by AI. LogID is filled in by the warehouse. The other columns store which procedure failed, the SQL error number, the message, the line, and the time. Nothing writes here until a load fails. If the Gold procedure rolls back, this table is how you can still see what went wrong.) 
and 'dbo.ingest_watermark' (also suggested by AI. it remembers how far the last successful copy got. One row per table, for Sales.SalesOrderHeader and Sales.SalesOrderDetail only. WatermarkValue is the latest ModifiedDate already copied. A later incremental run copies only rows newer than that. The first run is a full overwrite, so this table stays empty until you deliberately choose incremental.)
'dbo.ETL_Log' has LogID (bigint; A number the warehouse assigns to each error row, so the rows stay in order), ProcedureName (varchar 128; Which procedure failed. For this project that is dbo.usp_Load_Gold.), ErrorNumber (int; The SQL Server error code, such as a duplicate key or a missing object.), ErrorMessage (varchar 4000; The text of that error, readable without opening the pipeline log.), ErrorLine (int; The line inside the procedure where the statement failed.), LoggedAt (datetime2; When the error was written.)
'dbo.ingest_watermark' has SchemaName (varchar 128; Source schema of the table being copied. Here it will be Sales.), TableName (varchar 128; Source table. Only SalesOrderHeader or SalesOrderDetail.), WatermarkColumn (varchar 128; Which column marks “already copied.” For both tables that is ModifiedDate.), WatermarkValue (datetime2; The latest ModifiedDate successfully copied. The next incremental run takes rows newer than this.), UpdatedAt (datetime2; When that watermark was last saved.)
A full run does not need ingest_watermark. An incremental run does. ETL_Log stays empty on a successful load.

Made pipeline, it has 'lookup activity' and 'foreach activity' with 'copy data activity' inside it. The output of 'lookup activity' is input of 'for each activity' such that there were two outputs, i.e count and values. count was used by for each to iterate and values were used by copy data activity inside foreach activity.
'lookup activity' has query which is used to fetch both dest and source schemas, dest and source tables, source_query (for copy data functionality; The script builds source_query from sys.columns instead of using SELECT * but changed data types of some columns as delta tables didnt supported them like TimeSpan), primary keys, is_core (1 if gold or silver uses it, 0 if bronze keeps it), load_strategy(watermark for Sales.SalesOrderHeader and Sales.SalesOrderDetail means it will upsert; full i.e overwrite for other 67 tables), watermark_column (ModifiedDate) and counts of tables

'for each' runs on the base of 'count' and it is given 'value' as input.
copy jobs gets 'value', it then uses 'value.@item(dynamic var).source_query' to copy table from sql server to lakehouse and value.@item.dest_schema and value.@item.dest_table as destination of copy data activity

writing mode is 'overwrite' for copy data and it has retry policy of 2 with interval of 30 seconds and timeout of 15 mins.
changed data types of several columns as delta tables didnt support them as 'time' as it has TimeSpan, xml columns to text, 'hierarchyid' to text, 'geography' to text. phhotos and docs were left out.
